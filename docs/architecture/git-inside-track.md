Brief: [git-inside-track.md](../plans/git-inside-track.md). Mockup (untracked,
per the `mockup-first` skill): `_mockup-git-inside.html`. Decisions: journal
`git-theory-track`. Supersedes the theory half of

## What it is

A second git track, `git-inside`, shown by a segmented control inside the Git tab
next to the practical one, under the name **Inside git**. It explains what a
repository is MADE OF, is standalone - a learner may open it having never used
git - and contains **no commands anywhere**, which is what keeps it from being
the practical track with a cutaway view.

## Contract: the scene - one, with three lenses

A step declares `lens: "folder" | "chain" | "both"` over one `StoreState`.
Author-chosen per step; no learner toggle - the caption and the picture must
always agree. One data shape and one resolver, so the lenses cannot drift.

| Lens | Answers | Used when the lesson is about |
|---|---|---|
| `folder` | Where does this live, what is in it? | a new kind of FILE in `.git` |
| `chain` | Who names whom? | a RELATIONSHIP between objects |
| `both` | Are these two pictures the same? | the first complete save, and each part recap |

**Measured authoring rules.** MemoryViz gives the visual panel 562px at a 1440
viewport (729px at 1920; full width below 1280), and existing viz lessons run
about 487px tall. So the `chain` lens is COMPACT ROWS with a naming rail - one row
per object, each carrying a `names <id>` chip that matches another row on screen.
A horizontal chain needs 664px and wraps into an unreadable order; a vertical
stack of boxes reaches 721px and pushes the last object below the fold. Nesting is
worse than tall: it draws the parent commit inside the child, and a commit names
its parent rather than containing it. A `both` step costs the sum - four objects
sits at 478px, six reaches 630px - so keep `both` to the first complete save and
give a part recap the `chain` alone.

## Contract: the object store

- Real SHA-1 over the real object format (`blob 12\0hello world\n`). The id on
  screen is what `git hash-object` prints on the learner's machine. **This is a
  hard requirement, not a nicety** - the whole track rests on "the name comes from
  the content", and a fake hash makes that an article of faith.
- SHA-1 is implemented in plain JavaScript, not taken from `crypto.subtle`, which
  is absent outside a secure context and async - a promise inside every render.
  Proven against real git's ids in `_verify-store.mjs`.
- Objects are `blob | tree | commit`. Names are `refs/*` files holding one id,
  plus `HEAD` holding a ref name. The index is a path-to-id list.
- Nothing is ever mutated. Reachability is a walk from the refs.
- This is a NEW model, beside `git-model.ts`, not an extension of it. The
  practical model is a commit DAG with display-only hashes and cannot carry this.

## The three traps that decide whether the ids are real

Verified against git 2.34.1; vectors in `poc-git-vectors.json`, regenerated by
`poc-git-vectors.sh`. The header length is in **bytes**, so `café\n` is `blob 6`.
A tree entry carries the id as **twenty raw bytes** while a commit carries the
same id as **forty hex characters** - one serialiser cannot do both. Tree entries
sort as if every directory name ended in `/`, so `a.txt` comes before a directory
`a`, and the mode written into the object is `40000`, not the `040000` that
`git cat-file -p` prints.

## Contract: the playground

One widget, three levels, no commands: type content and see its real id; assemble
a tree from blobs and a commit from a tree; point a ref at a different object.

## Concept ownership

The practical track owns the command vocabulary (`gt-branch`, `gt-head`,
`gt-merge`, `gt-reset`, ...), moved there when the old theory lessons were
deleted. Inside git owns internals ids only, and where the two meet they use
DIFFERENT ids: practice owns `gt-staging-area` (the pile), theory owns the index
file. `gt-parent` was dropped with the old lessons and returns here.

## Tests, success signal, out of scope

`code-lab`: 27 unit tests (hashing, serialisation, the act vocabulary,
reachability) against a fixture generated by running real git, plus 10 DOM tests
for the three lenses. Course-side, `test/vendor-bundle.test.js` asserts the
vendored bundle still evaluates and still agrees with git.

Success signal: one end-of-track question answerable only if the object model
landed - a colleague force-pushed over your commit; is it gone, and how would you
know?

Out of scope: zlib framing beyond the one line the hash needs, delta encoding
inside packfiles, submodules, worktree plumbing, `rebase --onto`, the reflog file
format.
