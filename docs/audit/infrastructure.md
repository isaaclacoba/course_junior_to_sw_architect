# Infrastructure report - shared engines and page scaffold

This is not a lesson. It documents the reusable machinery every lesson is fed
into, so the per-lesson reports can stay about content. Read-only audit.

## The pieces

| File | Role |
|---|---|
| `page-shell.js` | Renders the hero and, for `drill`/`build` archetypes, the card scaffold, from a small `window.PAGE` config. Element ids are `prefix + suffix` (e.g. `cf` + `Title`). |
| `drill-engine.js` | Fill-in-the-blank + optional multiple-choice quiz engine. Reads `window.DRILL_CONFIG`. Powers theory lessons and runnable drills. `{{n}}` snippet markers become blank inputs. |
| `build-engine.js` | Write-from-scratch engine (Monaco editor, Run, output match). Reads `window.BUILD_CONFIG`. Grades by output match + optional `requireSource` technique gate + optional hidden `verify` probe. Supports prose formatting (paragraphs, `-` bullets, `**bold**`). |
| `styles.css` | All shared styling. Per-lesson CSS lives here, not per page. |
| `index.html` | The course path: track switch (Practical / Theory), stage heads, lesson cards. Reads per-card `data-key` / `data-total` from `localStorage` for status, progress bar, XP and the smart CTA. |
| `vendor/code-lab/` | Vendored IIFE bundle of the `code-lab` submodule: Monaco wrapper, guided tour, error panel, and the `RoslynIframeRunner`. `CodeLab.loadMonaco()` injects the AMD loader; `CodeLab.MemoryViz` / `CodeLab.Quiz` power the theory visuals and checkpoints. |
| `level3-app/` | Published (git-ignored) Blazor/Roslyn WASM host. Every Run button and the capstone load it over HTTP. Regenerated by CI; never hand-edited. |

## Config contracts (the repeatable surface)

- **`DRILL_CONFIG`** - `prefix`, `metaLabel`, `progressNoun`, `awardedKey`,
  `awardAmount`, `drills[]`. Each drill: `title`, `concept`, `context`,
  `snippet` (with `{{n}}` blanks), `points[]`, `blanks[{ id, label, answer,
  accept?, hints[], explain[{ text, highlight }] }]`, optional `quiz`, optional
  final `summary` recap card. Runnable drills add index-aligned
  `runnablePrograms[]` + `runnerUrl` + `xpKey`.
- **`BUILD_CONFIG`** - `prefix`, `tasks[]`, `runnerUrl`, `xpKey`, `awardedKey`,
  `awardAmount`. Each task: `title`, `concept`, `context`, `example?`, `goal[]`,
  `expected` (string or ordered array), `requireSource?[{ pattern, message }]`,
  `verify?{ main, expected, message }`, `starter`, `solution`.
- **Theory visual** - a `theory-N.viz.js` sets up a `CodeLab.MemoryViz` (or
  board+code) widget with a `chip` and ordered `steps[]` (each with `narr`).
  Loaded by `theory-N.html` before `page-shell.js`.
- **Checkpoints** - `theory-check-N.js` drives `CodeLab.Quiz` with a question
  bank, `passRatio`, and a per-attempt draw count.

## Infrastructure-level findings

1. **Two theory engines coexist, and one set of data files is dead.** Every
   shipped `theory-N.html` (1-21) loads the `theory-N.viz.js` visual widget. The
   sibling `theory-N.js` `DRILL_CONFIG` files are still on disk but are **not
   loaded by any HTML** - ~21 orphaned files. They are the earlier drill-engine
   version of the theory track, superseded by the MemoryViz conversion. This is
   the single biggest housekeeping item: decide to delete them or re-home them,
   and update `docs/course-overview.md` (which still implies the drill version).
2. **Grading strength is uneven by engine.** `build-engine` supports a hidden
   `verify` probe that re-runs the learner's code with different inputs to block
   hardcoding, but several build lessons (`writing-methods`, `lambdas`,
   `testing-basics`, `test-doubles`, `first-builds`) do not set one, so a
   hardcoded constant can pass. `data-shapes`/`generics` use probes well and are
   the model to copy.
3. **Runnability is inconsistent.** `drill-engine` supports `runnablePrograms`
   (Run button), but `control-flow` and `linq` ship without them while
   `collections`, `errors-null` and `reading-objects` are runnable - so two
   high-value lessons miss the "see it execute" payoff.
4. **`styles.css` centralisation holds** - lessons do not carry bespoke CSS,
   which keeps the repeatable structure clean.
5. **The `prefix + suffix` id convention** is the load-bearing rule for
   `page-shell`; any new lesson must set a unique `prefix` and matching
   `awardedKey`/`data-key`, or progress tracking silently breaks.
