# Shared JS engines - SOLID audit

Read-only review of `build-engine.js`, `drill-engine.js`, and `page-shell.js` - the three shared controllers that turn per-lesson config (`BUILD_CONFIG`, `DRILL_CONFIG`, `PAGE`) into a rendered, graded, runnable lesson. SOLID is applied pragmatically to procedural/modular JS - these are single IIFEs, not class hierarchies, so the useful lenses are SRP (does one unit do too much), OCP (must you edit to extend), and DIP (hard-wired concretes vs seams). LSP/ISP have almost no surface here.

## Findings

- **[S - high]** `drill-engine.js` (whole IIFE) - one closure owns config parsing, XP + `localStorage`, text helpers (`norm`, `canonical`, `withGaps`, `escapeHtml`, `renderInline`, `renderProse`), a code-line highlight subsystem (`applyCodeHighlight` with `getBoundingClientRect` geometry), a full modal "explain" overlay subsystem (`ensureExplainOverlay`, `showExplainOverlay`, `updateOverlayClipPath`, `positionExplainCard` - roughly 120 lines of DOM + clip-path math), mermaid rendering, the quiz subsystem (`renderQuiz` with Fisher-Yates shuffle, `quizAnswered`, `setQuizFeedback`), grading (`check`), and runner orchestration (`runExample`). At least five independent concerns live in one unit. Why it matters: any change to the overlay, the quiz, or the grader means editing the same 700-line closure, and none of these pieces can be unit-tested in isolation because they are private to the IIFE and coupled to the live DOM.

- **[S - high]** `build-engine.js` (whole IIFE) and its `run()` / `render()` - the closure mixes config parsing, `localStorage` XP, prose rendering (`escapeHtml`, `renderInline`, `renderProse`), grading (`matches`, `unmetRequirement`, `buildProbe`, `passesHiddenVerify`, `describeExpected`), runner orchestration, editor mounting, and navigation. `run()` alone compiles, inspects errors, sets editor markers, decides output vs runtime-error vs mismatch vs unmet-requirement vs hidden-verify, awards XP, and paints three result surfaces. Why it matters: the grading policy (the interesting, change-prone logic) is welded to DOM side effects, so you cannot exercise "does this output pass" without a browser and a running Roslyn host.

- **[S - high]** `build-engine.js` + `drill-engine.js` (cross-file duplication) - `escapeHtml`, `renderInline`, `cardFromHash`, `showOutput`, `showErrors`, `clearErrors`, and the XP block (`loadXP`/`loadCourseXP`, award/markAwarded, the `awarded` JSON read) are re-implemented in both files with small drift (build's `renderInline` also handles `**bold**`; drill's does not). Why it matters: this is the same responsibility copied, not shared - a fix or policy change (for example how XP is stored) must be made twice and kept in sync by hand, which is exactly the failure mode SRP + a shared module would prevent.
  - **FIXED.** All of these now live once in `window.LessonCommon` (`page-shell.js`, loaded before both engines) and each engine delegates to it: `escapeHtml`, `renderInline` (unified on the `**bold**`-aware version) and `cardFromHash`; `createProgress({storage, xpKey, awardedKey})` for the XP/awarded block; and `createOutputPanel({output, errors})` for `showOutput` / `hideOutput` / `showErrors` / `clearErrors` (the differing element containers are injected). The shared, DOM-free `createProgress` and `createOutputPanel` are unit-tested (`test/lesson-common.test.js`).

- **[D - high]** `drill-engine.js` and `build-engine.js` (XP functions) - both talk to `localStorage` directly (`localStorage.getItem(xpKey)`, `setItem`, and the `JSON.parse(localStorage.getItem(awardedKey) || "{}")` init). There is no storage abstraction to substitute. Why it matters: XP/award progression - real logic worth testing - is untestable without a DOM `localStorage`, and there is no seam to swap in a mock or a different backing store.
  - **FIXED.** `LessonCommon.createProgress` reads/writes through an injectable `storage` (default `LessonCommon.storage` = `localStorage`, with an in-memory fallback and a `memoryStorage()` factory). Both engines use it, so XP/award logic is now tested with a fake store and no direct `localStorage` remains in either engine.

- **[D - medium]** `build-engine.js` (top) and `drill-engine.js` (top) - hard dependencies on global concretes: `new CodeLab.RoslynIframeRunner`, `new CodeLab.MonacoEditor`, `CodeLab.showErrorPanel`, `CodeLab.loadMonaco`, `window.monaco.editor.colorize`, `window.Prism`, `window.mermaid`. The engines reach for these globals directly rather than receiving them. Why it matters: you cannot run or test an engine against a fake runner/editor; the coupling to `window.CodeLab` is implicit and only partially guarded (drill guards `window.CodeLab` before constructing the runner and before `showErrorPanel`; build assumes `CodeLab` exists at construction and would throw if it does not).

- **[S - medium]** `page-shell.js` (`PRACTICAL` / `THEORY` arrays + nextHref resolution) - the shell also owns the entire course ordering as two hard-coded filename lists and the logic that maps the current page to its successor. That is navigation/curriculum data, a separate concern from "render the hero and card scaffold". Why it matters: adding, reordering, or renaming a lesson forces an edit to the rendering shell, and the ordering cannot be reused (for example by the index page) without importing the shell.

- **[O - medium]** `page-shell.js` (`page.archetype === "drill" ... else if === "build"`) - supporting a new archetype requires editing the shell: adding another big card-template function and another branch. The card scaffolds (`drillCard`, `buildCard`) are large HTML string literals whose element ids must match the engine's `prefix + suffix` lookups, so shell and engine are coupled by an implicit id contract that is not expressed anywhere. Why it matters: the shell is not open for extension - every new lesson shape edits closed code, and a mismatch between a renamed id here and the engine's `el("...")` fails silently at runtime.

- **[O - medium]** `drill-engine.js` (`mode === "theory" ? ... : ...`) - the theory/code split is a conditional threaded through `render()`, `renderProse`, the fill-section heading, and the result copy. A third rendering mode means editing each of those branches rather than registering a new renderer. Why it matters: mode-specific behaviour is scattered, so extensions touch many points and risk missing one.

- **[O - medium]** `build-engine.js` (`run()` grading pipeline) and `drill-engine.js` (`check()` fuzzy match) - the grading strategy is inlined as fixed branches. Build's order (compile -> runtime -> `matches` -> `unmetRequirement` -> `verify`) and drill's exact/close/wrong heuristics are hard-coded; a lesson cannot supply an alternative grader without editing the engine. Why it matters: grading is the most lesson-specific policy, yet it is the least configurable part - new grading needs would fork the engine.

- **[O - low]** `build-engine.js` (`matches`) - `expected` branches on `Array.isArray` (ordered-sequence vs any-line-equals). This is a small, contained two-case switch and is acceptable, but it is still a type-branch that a third match mode would have to edit. Worth noting, not worth changing.

- **[L/I - n/a]** There is effectively no polymorphism or interface surface in these files - no subtype substitution and no client-facing interfaces to keep lean - so LSP and ISP do not meaningfully apply. The nearest thing is the config object shape each engine consumes; those are already narrow and optional-friendly.

## What's fine

- The grading helpers in `build-engine.js` (`matches`, `unmetRequirement`, `buildProbe`, `passesHiddenVerify`, `describeExpected`) are individually small, single-purpose, and mostly pure - good internal decomposition even though they share the file.
- `page-shell.js` `heroHTML`, `drillCard`, and `buildCard` are pure string builders with no side effects - clean and easy to reason about.
- Config-with-defaults (`cfg.runnerUrl || "..."`, `cfg.xpKey || "course_global_xp"`, `awardAmount`, `awardedKey`) is a lightweight injection seam: the runner URL, XP keys, and award amount are genuinely configurable per lesson - a partial DIP win.
- Element ids are derived from a `prefix` in both engines (`el = (suffix) => document.getElementById(prefix + suffix)`), so a controller is not bound to one specific page's markup.
- `drill-engine.js` constructs the Roslyn runner only when `runnablePrograms.length && window.CodeLab` - it does not pay for the compiler on pure-theory pages, and it guards the global before use.
- All three files guard their required config and fail loudly (`console.error` + early return) when `DRILL_CONFIG` / `PAGE` / hero are missing.
- `page.nextHref` can be overridden per page, so the built-in course order is a default rather than a hard rule.
- The prose renderers (`escapeHtml` + `renderInline`) are pure and correctly escape before wrapping - no obvious injection of raw untrusted markup through those paths.

## Verdict

The engines work and share sensible small helpers, but both `drill-engine.js` and `build-engine.js` are monolithic IIFEs that fold five-plus concerns - rendering, grading, XP/storage, overlays, and runner orchestration - into one untestable closure, with several of those concerns duplicated across the two files. The strongest, most actionable issues are SRP (the embedded overlay/quiz/grader subsystems) and DIP (direct `localStorage` and `window.CodeLab` coupling with no seam), which together make the change-prone grading and progression logic impossible to test without a live browser and compiler. OCP is a secondary concern: `page-shell.js` closes its archetype and course-order logic to extension, so new lesson shapes edit existing code rather than plugging in.
