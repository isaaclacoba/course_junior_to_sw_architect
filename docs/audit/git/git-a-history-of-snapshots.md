## Concept(s) taught
What makes a row of commits a history: the parent link. Each commit points backward at the one it was built on, and that chain is what `git log` walks.

| # | Step | Concept | What the learner sees |

## Prerequisites
Assumes lesson 1 (`git-first-commit`) - the learner has seen commits appear on a graph, and has typed `git add` and `git commit`. This lesson explains the LINE between the dots.

## Complexity rung
A small conceptual step: from "dots appear when you commit" to "each dot remembers the one before it, and that is why git can look back." No new commands.

## Gaps / issues

**Theory adds almost nothing new.** The owner's complaint: "Theory and practice are identical - theory adds nothing." Let me check what lesson 1 already showed:

Lesson 1, card 3 `context`:
> "This repository already holds one commit - `add cat`.\n\nSaving `dog.txt` does not replace it. The new commit points back at the old one, and the graph draws the link. That is all a history is: each snapshot remembering the one before it."

Lesson 1's card 3 already states that "the new commit points back at the old one" and defines a history as "each snapshot remembering the one before it." This theory lesson repeats that statement across 5 steps with nearly identical wording.

What this lesson DOES add:
- Names the concept `parent` (introduced here, per `meta.js`).
- Shows the direction explicitly: "each commit points **backwards**."
- Explains what `git log` does: "walks the chain by following parents."

But: lesson 1 already drew the graph with the links visible, so the visual is not new. The narration restates what lesson 1's prose said in one paragraph.

**What is missing from BOTH lessons:** Neither lesson 1 nor lesson 2 explains WHY the parent link matters - what you can DO with it (compare versions, undo, find what changed). They assert "this is a history" without showing the consequence.

**Card/step count judgment:** 5 steps for one concept (that commits point backward) is thin, but acceptable for a consolidation lesson - IF the concept were new. Since lesson 1 already stated it, this feels like padding.

**Actionable fixes (per `git-track-depth.md` ratified decision "theory explains the MODEL"):**
1. **Show file contents changing.** Add a second panel showing the text of `cat.txt` in commit 1, then `dog.txt` appearing in commit 2, then `bird.txt` in commit 3 - so "snapshot" becomes concrete instead of abstract. Require the model's file-text feature (phase 1 of `git-track-depth.md`).
2. **Contrast commit and working tree.** Show step 3's narration alongside a panel displaying: "Commit 2 holds `cat.txt` and `dog.txt`. Commit 1 holds only `cat.txt`. The parent link is how git knows what CHANGED." This makes the parent link functional, not just a line.
3. **OR: Merge this lesson into lesson 1's summary.** If theory stays read-only, demote this to a 2-step recap inside lesson 1's summary panel, and use the freed lesson slot for the missing three-areas theory lesson.
